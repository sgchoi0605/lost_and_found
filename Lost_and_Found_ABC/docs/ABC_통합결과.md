# ABC 통합 결과

2026-11-25. `Lost_and_Found`의 공통·계정 코드, `Lost_and_Found_B/features/reports`, `Lost_and_Found_C/features/discovery`를 통합했습니다. 원본 세 폴더는 변경하지 않았습니다.

## 실행

Node.js 22.13 이상이 필요합니다. pnpm 10.34.9와 기존 pnpm-lock.yaml을 사용합니다.

```sh
pnpm install --frozen-lockfile
pnpm db:init
pnpm start
```

`http://127.0.0.1:3000`에 접속합니다. 회원가입 후 `pnpm admin:promote <아이디>`로 해당 사용자를 관리자로 지정할 수 있습니다. 개발용 Vite는 별도 터미널의 `pnpm dev`로 실행합니다. Vite만 실행하면 API는 작동하지 않습니다. `pnpm build`는 프론트엔드 빌드 검사이며 Express 서버를 대체하지 않습니다.

pnpm이 PATH에 없으면 Node.js의 `npm run db:init`, `npm start`, `npm test`, `npm run build`도 사용할 수 있습니다. 의존성의 재설치는 pnpm 잠금 파일을 기준으로 합니다.

## 구현과 정책

- A: 가입, 로그인, DB 세션, 알림 목록·읽음, 관리자 사용자 제한, 서버·공통 보안.
- B: 분실·습득 신고, 사진, 본인 수정·삭제, 관리자 검색·접수·보관, 페이지 이동.
- C: 검색·상세·유사 물품 후보·관리자 확정/거절/해제·통계.
- D: 테이블·화면 골격만 있으며 인계·보관 기한·폐기·이관 API는 아직 미구현입니다. 상세보기의 인계 신청은 준비 중으로 표시합니다.

신고 관리의 상태 전이는 `REPORTED → RECEIVED`, 습득물에 한해 `RECEIVED → STORED`입니다. `MATCHED`는 C에서만 변경하며 인계·폐기 등의 상태를 B에서 직접 지정할 수 없습니다.

신고의 수정·삭제·B 상태 변경은 확정된 매칭, 거절되지 않은 인계 신청, D 보관 기록이 있으면 HTTP 409 `REPORT_LOCKED`로 차단합니다. 기본 신고 상태가 아닌 경우도 차단합니다. 확정 매칭은 C의 정식 해제 후 수정·삭제할 수 있습니다. D 기록이 있는 물품의 해제는 향후 D 업무 절차가 필요합니다.

신고 수정·삭제 시 일반 매칭 후보는 C 서비스가 삭제하고 `MATCH_INVALIDATE` 감사 이력에 이전 후보 전체를 보관합니다. 이미 거절한 매칭은 유지합니다. 후보 무효화와 신고 변경은 같은 트랜잭션이므로 실패 시 함께 취소됩니다. 매칭 생성은 사용자가 매칭 화면에서 실행하는 방식이며 신고 등록 시 자동 실행하지 않습니다. 수정 후에는 다시 후보 생성을 실행합니다.

C의 검색·상세·매칭 생성은 `req.db`로 전달받은 동일 DB 연결을 사용합니다. 확정 직전에 최신 신고 정보로 유사도와 후보 자격을 다시 검사합니다.

## 보관 장소와 시간

DB 버전은 3입니다. `reports.storage_place`는 신고자가 입력한 보관 장소이며 D의 실제 보관 접수 기록이 아닙니다. D 연동 시 이 값을 초기 입력으로 사용하되 실제 보관 장소·접수일·기한은 `storage_records`에서 관리해야 합니다.

`db:init`은 v1/v2 DB를 보존하면서 v3로 이전합니다. v2 습득 신고 설명의 `[보관 장소: ...]` 접두사는 별도 컬럼으로 옮기고 설명에서는 제거합니다. 이 작업은 트랜잭션으로 처리되며 재실행해도 중복 이전하지 않습니다. 원본 폴더의 DB는 복사하지 않았습니다.

신고 입력은 날짜·시간을 받고 브라우저 현지 시간을 UTC ISO로 전송합니다. 수정 화면은 현지 시간으로 복원합니다. 기존 날짜 전용 API 입력은 호환을 위해 UTC 자정으로 해석합니다. C의 날짜 필터와 통계 기간은 기존 UTC 기준을 유지합니다.

## 검사

`pnpm test`는 공통·A·B·C 및 `tests/integration.test.js`를 실행합니다. 임시 DB와 업로드는 `.tmp/` 아래에만 생성합니다. 개별 검사도 `pnpm test:account`, `pnpm test:reports`, `pnpm test:discovery`, `pnpm test:integration`으로 실행할 수 있습니다.

통합 회귀 검사는 회원가입부터 매칭·알림까지의 HTTP 흐름, 확정 매칭 보호, 후보 무효화, 실패 시 롤백, 상태 전이, 인계/보관 충돌, 50건 초과 페이지 이동, 관리자 검색 및 v2 DB 이전을 확인합니다.

## D 구현 시 남은 작업

- 인계 신청 URL의 `foundReportId`를 읽고 소유자 증빙을 받는 실제 API 연결.
- 승인 `APPROVED`와 인계 완료 `COMPLETED` 분리, 수령인·완료 시각 기록.
- 보관 기간, 임박 알림, 폐기·이관 상태와 감사 이력을 동일 트랜잭션으로 처리.
- C 매칭 해제와 D 진행 상태의 충돌 규칙 유지.
