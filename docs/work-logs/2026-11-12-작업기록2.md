## 완료한 코드

### 1. 공통 DB 연결

`shared/backend/database.js`에 Node 내장 `node:sqlite` 연결 함수를 구현했다.

- `openDatabase()`로 연결하고 사용한 쪽에서 `close()`한다.
- 기본 DB 파일은 `database/lostfound.db`다.
- `.env`의 `DATABASE_PATH`로 변경할 수 있고 상대 경로는 프로젝트 루트 기준이다.
- DB 파일의 부모 폴더가 없으면 만든다.
- 모든 연결에 외래 키 검사를 활성화하고 잠금 대기 시간을 5초로 설정한다.
- import나 웹 서버 시작만으로 DB를 만들거나 초기화하지 않는다.

### 2. 초기화 명령

`shared/backend/init-db.js`와 `pnpm db:init` 명령을 구현했다.

- account → reports → discovery → operations 순서로 스키마를 적용한다.
- 전체를 트랜잭션으로 묶어 중간 오류가 생기면 롤백한다.
- 반복 실행해도 기존 데이터를 지우지 않는다.
- 외래 키 위반을 점검하고 `PRAGMA user_version=1`로 버전을 기록한다.
- 현재보다 높은 DB 버전이면 작업을 거부한다.
- 성공·실패에 관계없이 CLI의 DB 연결을 닫는다.
- 기존 컬럼 변경을 자동 처리하는 마이그레이션 기능은 아니다.

## 추가 설명 — 스키마와 DB 파일은 무엇이 다른가?

추가일: 2026-11-12

**스키마는 데이터베이스의 구조와 규칙이다.** 어떤 테이블이 있고, 각 테이블에 어떤 컬럼을 두며, 어떤 값을 저장할 수 있고, 테이블끼리 어떻게 연결되는지를 뜻한다.

예를 들어 이 프로젝트의 스키마에는 다음과 같은 내용이 포함된다.

- users에는 user_id, login_id, email 등의 컬럼이 있다.
- login_id는 필수값이고 중복될 수 없다.
- reports.author_id는 실제 존재하는 users.user_id를 참조해야 한다.
- reports.report_type에는 LOST 또는 FOUND만 저장할 수 있다.
- 자주 조회하는 컬럼에는 인덱스를 두고, 잘못된 관계는 트리거로 막는다.

따라서 “테이블을 만드는 명령어 모음집인가?”라는 이해는 **이 프로젝트의 schema.sql 파일을 설명할 때는 대체로 맞다.** 다만 스키마는 구조 자체이고, `.schema.sql` 파일은 그 구조를 만들기 위한 SQL 명령을 적은 텍스트 파일이다. 여기에는 CREATE TABLE뿐 아니라 인덱스와 트리거를 만드는 명령도 들어 있다.

| 구분 | 의미 | 프로젝트의 예 |
|---|---|---|
| 스키마 | 테이블·컬럼·자료형·관계·제약 등 구조와 규칙 | reports.author_id가 users를 참조한다는 규칙 |
| 스키마 SQL 파일 | 그 구조를 생성하는 명령을 담은 텍스트 | features/reports/reports.schema.sql |
| DB 파일 | 실제로 생성된 구조와 저장된 데이터 등을 담은 SQLite 파일 | database/lostfound.db |
| 행 데이터 | 테이블에 들어 있는 실제 기록 | 특정 사용자가 등록한 지갑 분실 신고 한 건 |

**DB 파일에는 데이터만 있는 것이 아니라 적용된 스키마도 함께 들어 있다.** 그래서 DB Browser에서 같은 파일을 열어 테이블 구조와 데이터를 모두 볼 수 있다. 현재 파일은 스키마가 생성되어 있지만 사용자·신고 데이터는 비어 있는 상태다.

현재 생성 과정은 다음과 같다.

```text
기능별 *.schema.sql 파일 4개
           ↓ pnpm db:init
shared/backend/init-db.js가 순서대로 실행
           ↓
database/lostfound.db에 8개 테이블·인덱스·트리거 생성
           ↓ 이후 업무 API 구현
회원·신고·매칭·인계 데이터를 행으로 저장하고 조회
```

## 팀원들은 이 DB를 어떻게 활용하는가?

### 1. 같은 설계를 받고 자기 컴퓨터에 DB를 만든다

GitHub에서 최신 스키마와 DB 연결 코드를 받은 뒤 프로젝트 루트에서 실행한다.
이번 변경은 A 브랜치에 있으므로 B·C·D도 해당 변경이 자기 작업 브랜치에 반영되어 있어야 한다. 자기 브랜치에서 pull만 했다고 A의 변경이 자동으로 들어오는 것은 아니다. 팀의 PR·통합 절차에 따라 반영한다.

```powershell
corepack pnpm install
corepack pnpm db:init
corepack pnpm test:db
```

- 각자의 컴퓨터에 같은 구조의 database/lostfound.db가 생성된다.
- 실제 DB 파일은 Git에 올리지 않는다. 공유하는 것은 SQL·초기화 코드·계약 문서다.
- 따라서 B의 로컬 DB에 넣은 신고가 C의 로컬 DB에도 자동으로 생기지는 않는다.
- 같은 테스트 데이터를 원하면 별도의 공통 seed 스크립트를 만들어 공유해야 한다. 현재 seed 스크립트는 없다.
- 최종 통합 시 하나의 실행 중인 백엔드가 사용하는 DB를 통해 데이터를 공유한다. 각자 PC에서 따로 실행 중인 서버는 서로 다른 DB를 사용한다.

### 2. 담당 기능의 백엔드에서 공통 연결 함수를 사용한다

브라우저의 HTML/JS가 SQLite 파일을 직접 열도록 만들지 않는다. 화면은 서버 API를 호출하고, 서버의 repository가 SQL을 실행하도록 연결한다.

```text
브라우저의 frontend/js
    ↓ fetch로 API 요청
기능별 backend/index.js의 Router
    ↓
controller: 요청과 응답 처리
    ↓
service: 로그인·권한·입력값·업무 규칙 확인
    ↓
repository: openDatabase()로 연결하고 SQL 실행
    ↓
database/lostfound.db
```

다음은 B의 `features/reports/backend/report.repository.js`에서 사용할 수 있는 **향후 구현 예시**다. 이 문서에 예시를 적은 것이며 해당 업무 함수를 실제 코드에 구현한 것은 아니다.

```javascript
import { openDatabase } from '../../../shared/backend/database.js';

// 로그인 검증을 거친 작성자 ID로 삭제되지 않은 신고 목록을 조회하는 예시입니다.
export function findReportsByAuthor(authorId) {
  const db = openDatabase();
  try {
    return db.prepare(`
      SELECT report_id, report_type, item_name, status, created_at
      FROM reports
      WHERE author_id = ? AND deleted_at IS NULL
      ORDER BY created_at DESC
    `).all(authorId);
  } finally {
    // 간단한 예시에서는 조회 후 연결을 닫습니다. 서버의 연결 재사용 정책은 추후 통일합니다.
    db.close();
  }
}
```

`?`에 값을 바인딩하므로 입력값을 SQL 문자열에 직접 이어 붙일 필요가 없다. `authorId`는 추후 서버 인증으로 확인한 사용자 ID를 서비스에서 전달해야 한다. 화면이 보낸 ID를 그대로 믿으면 다른 사람의 신고를 조회할 수 있으므로 실제 API에서는 권한 검증이 필요하다.

### 3. 팀원별로 담당 기능을 연결한다

| 담당 | DB를 활용할 작업 |
|---|---|
| A | users에 계정 저장·조회, notifications 읽음 처리, audit_logs 변경 이력 기록, 공통 연결·초기화 관리 |
| B | reports 신고 등록·조회·수정·논리 삭제, report_photos 사진 경로 관리 |
| C | reports 조건 검색·통계 조회, matches 후보 저장·조회·확정 |
| D | handover_requests 신청·심사·완료, storage_records 보관·폐기·이관 관리 |

모든 기능은 같은 프로젝트 DB를 사용하지만 각자 담당 기능의 백엔드를 구현한다. 다른 기능의 데이터를 읽거나 변경할 필요가 있으면 API·데이터 계약을 먼저 맞추고 담당자와 연동한다. 특히 C의 검색·통계는 합의된 reports 컬럼을 조회하며, D의 인계 완료처럼 여러 테이블의 상태가 함께 바뀌는 작업은 트랜잭션과 책임 범위를 정해야 한다.

전체 DB 설계는 합의대로 A가 관리하므로 팀원이 임의로 컬럼을 추가하거나 이름을 바꾸지 않는다. 필요한 컬럼과 제약 변경을 A에게 요청하고, SQL·DB 설명·사용 코드를 함께 맞춘다.

### 4. 실제 화면 저장은 아직 후속 구현이 필요하다

DB가 만들어졌다고 기존 화면의 버튼이 자동으로 DB에 연결되지는 않는다. 현재 Router에는 연결 확인 경로만 있으며, repository·service·controller와 실제 업무 API를 구현해야 한다.

예를 들어 신고 등록은 다음 순서로 연결해야 한다.

1. A와 B가 신고 등록 API의 요청·응답 형식을 확정한다.
2. A의 인증 기능으로 서버에서 작성자를 확인한다.
3. B가 입력값과 권한을 확인하고 reports에 INSERT하는 백엔드를 구현한다.
4. 사진 경로도 저장한다면 report_photos와 함께 처리한다.
5. 화면의 신고 버튼이 해당 API를 호출하도록 연결한다.
6. DB Browser나 조회 API로 실제 저장 결과를 확인한다.

외래 키 때문에 작성자 users 행이 먼저 있어야 reports를 저장할 수 있다. 인증 구현 전 개발용 데이터를 직접 넣더라도 그것을 실제 로그인·가입 기능으로 설명하면 안 된다. 비밀번호는 이후 인증 구현에서 해시로 저장해야 한다.

### 5. 스키마 파일 수정과 기존 DB 변경은 별개다

현재 초기화 SQL은 CREATE TABLE IF NOT EXISTS를 사용한다. 이미 있는 테이블은 그대로 두므로, SQL 파일에 컬럼을 추가하고 db:init을 다시 실행하는 것만으로 기존 테이블에 새 컬럼이 생기지는 않는다.

- 새 DB: 최신 스키마로 처음부터 생성할 수 있다.
- 데이터가 있는 기존 DB: ALTER TABLE 등의 변경 SQL을 순서대로 적용하는 마이그레이션이 필요하다.
- DB 파일 삭제 후 재생성: 기존 데이터가 사라지므로 초기화를 위해 무조건 삭제하면 안 된다.

현재는 최초 스키마 버전 1까지 구현한 상태다. 이후 DB 변경 시에는 A가 마이그레이션과 팀원 적용 방법을 함께 제공해야 한다.
